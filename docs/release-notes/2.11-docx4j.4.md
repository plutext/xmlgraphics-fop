# docx4j-fo-renderer 2.11-docx4j.4 (DRAFT, 2026-10-03)

Draft; closes when Jason says the release goes. There is no 2.11-docx4j.3: that branch (2.11 plus
`fop/CR-008`) was never released, and this release follows 2.11-docx4j.2. The merge and `fop/CR-010` are
gated: through docx4j 17.3.0, the three corpora and the probes are unchanged against 2.11-docx4j.2. The runbook is `docs/developer/releasing.md`; the
version moves in the `revision` property of the root pom.

`docx4j-fo-renderer` is a modified distribution derived from Apache FOP 2.11, maintained for
docx4j's docx-to-PDF path. Apache FOP is a trademark of the Apache Software Foundation; this is not
an Apache release. Packages stay `org.apache.fop`; the fork and Apache FOP must never share a
classpath. Coordinates `org.docx4j:docx4j-fo-renderer`, `-core`, `-events`, `-util`.

## The base: Apache `main` after 2.11

Up to 2.11-docx4j.2 this renderer was the 2.11 release plus fixes. From this release it is Apache FOP's
`main` branch after 2.11, merged at ab5d6eba6 (2026-09-29), plus the same fixes (`fop/CR-009`). Apache
has released nothing since 2.11 and still versions `main` as 2.11.0-SNAPSHOT, so the version line
stays 2.11. It brings 91 upstream commits:
- memory: area traits deduplicated, the structure tree collectable, fewer `MinOptMax` objects, a PDF
  image cache;
- accessibility: tagging past the first page-sequence in the artifact case, footnote and table
  tagging under PDF/UA, link `/Contents`;
- security: temp files, SVG glyph DTDs, hyphenation deserialisation;
- leader rule styles, `fo:table-and-caption`, and Java 25.

Left out: FOP-3311 and FOP-3326 (PostScript only), which need `xmlgraphics-commons` API that no release
has. Batik 1.19 and `xmlgraphics-commons` 2.11 stay, since a Central release cannot depend on a snapshot.

For docx4j: `rule-style-int` keeps the leader area's `setRuleStyle(int)`, which `main` removed, so docx4j
17.3.0 runs unchanged. `fox:gsub-features` now has property id 296.

## Fixes since 2.11-docx4j.2

- **Both units of a surrogate pair resolve to one bidi level** (`fop/CR-008`, FOP-2918). A
  right-to-left character outside the BMP (Cypriot, Phoenician, Adlam and the like) no longer leaves a
  word with two levels. That failed an assertion under `-ea`; with assertions off, a word mixing such
  a character with Latin letters was drawn reversed, with `#` for the character. And a neutral outside
  the BMP inside right-to-left text no longer cuts the run in two. Not fixed: FOP's bidi class table
  predates Unicode 6.1, so U+1F600 and later emoji still count as left-to-right letters (CR-008 §5).
  Nothing moves in text without a character outside the BMP. Gated through docx4j: a probe that
  aborted under `-ea` on 2.11-docx4j.2 renders, and its two wrongly ordered lines take the order a
  BMP stand-in gets; corpora identical by construction.

- **A word's letter spaces are in its width for fonts with layout tables too** (`fop/CR-010`, Enterprise
  CR-001 item 16, FOP-2349, capability `letter-space-width`). Letter-spaced text in an OpenType font was
  measured without its spacing and overran the line. The merged FOP-2722 counted the spaces without
  their width, which would have regressed docx4j's letter-spaced documents; with this change they
  measure as on 2.11-docx4j.2.

- **A block nested in an inline keeps the text after it when FOP lays a paragraph out again** (`fop/CR-011`,
  Enterprise CR-001 item 36). After a float, or when the paragraph breaks onto a page of a different width,
  the lines after the nested block were dropped and FOP threw a `NullPointerException`. A nested block is
  how a line break inside a run reaches FO.
- **A line that overflows beside a float wider than the column is reported, not thrown** (`fop/CR-011`,
  item 37).

  Neither changes docx4j's output with Word layout on, where docx4j's own line manager carries the same
  fixes; both apply to FOP's own line manager (Word layout off, or plain FO).
