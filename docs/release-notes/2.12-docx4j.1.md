`docx4j-fo-renderer` is a modified distribution derived from Apache FOP, maintained for docx4j's

release. Packages stay `org.apache.fop`; the fork and Apache FOP must never share a classpath.
Coordinates `org.docx4j:docx4j-fo-renderer`, `-core`, `-events`, `-util`.

## Changes since 2.11-docx4j.8

- **The base is the Apache FOP 2.12 release, and the version line is `2.12`** (`fop/CR-030`). Apache released 2.12
  on 2026-10-20 from its branch `fop-2_12` (69e912b39). Its Java is that of Apache `main` at c2d7e0aca, the fork's
  base since `2.11-docx4j.7`, but for one javadoc line, so layout and rendering are unchanged by the base itself.
  FOP-3354, which reached `main` after 2.12's branch was cut, the fork already carries. `Docx4jFop.APACHE_FOP_LINE`
  is `"2.12"`. docx4j's `FopCapabilities.BUILT_FOR_LINE` must say `"2.12"` for this line; a docx4j built for
  `2.11` logs a warning at start-up.
- **Dependencies are Apache 2.12's:** Batik 1.20 (from 1.19), xmlgraphics-commons 2.12 (from 2.11), ant 1.10.18
  (from 1.10.14), bouncycastle 1.86 (from 1.85; `jdk15to18`, `provided` as before, so still not transitive).
- **If your build excludes Batik's transitive dependencies, check `xml-apis-ext`.** Under Batik 1.20 the
  `org.w3c.dom.svg` interfaces (`xml-apis:xml-apis-ext`) come only through `batik-css` and `batik-parser`. docx4j's
  exclusions lost them, and every SVG then failed with `NoClassDefFoundError: org/w3c/dom/svg/SVGDocument`. The fork's
  own dependency tree still carries `xml-apis-ext` 1.3.04; a consumer that excludes it, or those two modules, declares
  it, as `docx4j-export-fo` does from the 2.12 line.
- **PostScript output gains Apache's `jpeg-compression` and `compress-streams` options** (FOP-3311, FOP-3326). The
  fork had left them out since `2.11-docx4j.4` because they needed xmlgraphics-commons API no release had
  (`fop/CR-009` §3.1); commons 2.12 has it. docx4j never writes PostScript.
- **Correction to the `2.11-docx4j.8` note on `fop/CR-028`.** It said FOP's own `image` bridge on the PDF and
  PostScript paths applied no rule at all. That was wrong. Batik's `SVGImageElementBridge` asks the user agent in
  `buildImageGraphicsNode`, before FOP's override is reached, in Batik 1.19 and 1.20 alike. A `file:` picture in an
  `http:` document is refused on Apache FOP 2.12 and on a pre-CR-028 fork jar (`fop/CR-028` §2). The hole CR-028
  closes is unchanged and still open in Apache FOP 2.12: from a file base URI an SVG may draw any local file. The
  option `svg-embedded-resources-only` stays on by default.
